# Koperasi page and loans

### Koperasi page

- `/dashboard/payroll/koperasi` is Super Admin only. `?view=koperasi` (default) manages users/members; `?view=simpan-pinjam` retains the loan audit. The old `/dashboard/payroll/simpan-pinjam` redirects with HTTP 308, preserving other query parameters. The employee portal, `simpanPinjam` collection and `/api/koperasi/loans` are unchanged.
- Editable: Status Pembayaran, Iuran Pokok, Iuran Wajib, Role, and Status keanggotaan, plus an optional audit note. Rupiah inputs accept whole amounts from 1 to 10,000,000. `Pending Verification` can only be retained when already current. Staff roles require explicit confirmation because they grant permissions in the Koperasi app at next login. Every member edit also mirrors legacy `status` (`Pending` becomes `pending`). Names, identity/contact data and savings balances are not edited here.
- Payroll uses `koperasiSavingsAmounts`: approved members with `paymentStatus === 'Payroll Deduction'` pay their configured monthly contribution (zero/missing falls back to Rp25,000). Payroll-managed new members also pay Iuran Pokok once, in their assigned first payroll month (default Rp250,000), on its own payslip row. Subsidi Yayasan and other non-payroll states have no deduction or automatic credit. Explicit links take precedence over name fallbacks. Refresh updates drafts; locked/paid snapshots remain authoritative.
- Link candidates must be active and unlinked. Suggestions rank NIK, email, then normalized names with Koperasi overrides; search includes all available employees. Both employee collections are checked transactionally for `koperasiAuthUid` and `koperasiUserId`. UID falls back to the Koperasi document ID. Replacing a link explicitly checks the previous holder and clears it atomically. Converted-away Pekarya records are excluded from current matches but keep their historical links for the final Pekarya slip.
- Banks are read-only in this page: Loyalis `banking_info.bank_name/account_number` or Pekarya `bankAccount.bankName/accountNumber` is copied to Koperasi `bankDetails`. Bank names are preserved (BRIS remains BRIS); account numbers retain digits, including leading zeroes. Bulk sync previews differences and skips incomplete/empty SAKU banks. Employee bank saves, reverts and Pekarya-to-Loyalis conversions request a server sync as a best-effort step; a failure leaves the employee save intact and shows a message. The page continues to show differing banks.
- All Koperasi writes use `koperasiAdminDb()`, with HTTP 503 when credentials are absent. `PATCH /api/admin/koperasi-members`, `POST .../link`, and bulk `POST .../bank-sync` require Super Admin. Single-employee bank sync also permits `EMPLOYEE_PROFILE_EDITOR_ROLES`; browser bank values are never accepted. Browser rules prohibit creating non-null cooperative link fields or changing existing links, including for Super Admin; server link/conversion flows own them.
- Edits use an `expected` snapshot and return 409 on conflict. `FinancialAuditLogs` and `FinancialIdempotencyKeys/{uid}__{requestId}` live in SAKU. Cross-project edits/sync reserve a pending receipt before the Koperasi write, then atomically finish the audit and receipt in SAKU. This small extension to the three-step flow prevents concurrent request-ID reuse and preserves bank before-values across a lost response. Pending receipts are resumed, never replayed as success. Bank batches also check document versions. Link writes and their audit are one SAKU transaction; a pending bank-sync step can be retried without relinking.
- Loan decline: in the Simpan Pinjam audit view, Super Admin can **Tolak** a loan while it is Menunggu Persetujuan BAK, Menunggu Persetujuan Wakil Rektor 2 or Menunggu Transfer BAK (`canAdminDeclineKoperasiLoan`). `POST /api/admin/koperasi-loans/decline` (Super Admin only) needs a reason (max 500) and the `expectedStatus` the admin saw; a changed status returns 409. It writes what the Koperasi app's own rejection writes: `status: 'Ditolak BAK'`, `alasanPenolakan`, a history entry `Ditolak dengan alasan: …` with `updatedBy: internal-bak:<uid>`. Declining a restructuring hands its parent back `Disetujui dan Aktif` (only if the parent is still waiting on this request). `Ditolak BAK` is finished in both apps, so the member can apply again. Same receipt/audit flow as member edits (`KOPERASI_LOAN_DECLINED`); a fresh request on an already-declined loan is a 409, a resumed one finishes its audit once. The Koperasi app matches: BAK/Direktur also have Tolak at Menunggu Transfer BAK (`src/components/SimpanPinjam.js`).
- The member page reload invalidates both employee and Koperasi payroll query caches. The former Simpan Pinjam audit body is `src/components/koperasi/SimpanPinjamAuditView.tsx`; both views share one data load and retain URL-selected navigation.
- Verification: `npm test`, `npm run test:koperasi-members:integration` (Auth + Firestore emulators only, `firebase.koperasi-test.json` with `singleProjectMode: false` for `koperasi-unipdu`), `npm run build`, and a lint comparison against the pre-existing baseline. Production edits must use an agreed test member first.

### Employee registration and payroll savings

- **Daftarkan pegawai** registers an active Pekarya or Loyalis immediately. Superadmin selects the employee, email, initial password and payment status. The server assigns the first existing open/unsealed month after the latest closed payroll month; there is no month selector. Identity/contact and bank details come from SAKU. Missing email can be entered for the Koperasi login without changing the employee profile.
- Superadmin-only `GET /api/admin/koperasi-members` previews the first month and existing accounts (`employeeId`, `employeeCollection`, `email`). `POST` accepts those identifiers, `paymentStatus`, `initialPassword` for new Auth identities, optional `existingMemberId`, `note`, and `requestId`. Existing identity matches must be explicitly selected; ambiguous NIK/email matches are blocked. Existing passwords and roles are preserved. Passwords are never stored in receipts or audit records.
- `KoperasiEnrollments/{collection}__{employeeId}` and `KoperasiMemberEnrollments/{memberId}` reserve unique enrollment/ownership across retries. A member is staged pending, linked in SAKU, then activated in Koperasi. The receipt, final audit and completed enrollment are one SAKU transaction. Incomplete enrollment blocks payroll closure until its registration is retried and completed.
- Koperasi member `payrollSavings` stores `startPeriod`, `initialPeriod`, and `initialPaid`; balance changes never determine whether the initial contribution is owed. A subsidy member switching to Potong Gaji before paying the initial fee gets the current open month assigned for that fee. Later payroll cannot bypass an unpaid first-month fee.
- Bridge plan/receipt version 2 adds a frozen `savings` item with member identity, membership/payment policy and initial/monthly amounts. Draft save derives canonical contribution rows server-side. Closing a period validates current external plans and source links; locking applies loan progression and savings in one Koperasi transaction. The savings marker `payrollSavingsProgressions/{YYYY-MM}__{memberId}` prevents duplicate credits and another employee's slip from reusing the member. Logs remain visible through `tabunganLogs` and `tabunganLogsPerUser`, with `source: internal_bak_payroll`.
- The cross-project lock saga resumes after a lost response without charging again. Draft edits are held while external completion is uncertain. Existing historical version-1 plans/snapshots retain their hash and meaning; managed members require version 2 from their effective month. Scheduled/manual legacy jobs skip payroll-managed members transactionally. Payroll-generated savings logs cannot use legacy rollback.
